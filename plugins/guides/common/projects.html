{N}Projects and the job folder

The plugins work on one shared processing project per job, kept beside the mapper's day folders. The mapper's files are never changed: everything the plugins make goes in the project's own folder.

PathHolds
Greenstone/The job folder: the mapper's project folder, copied from the mapper as it is (read only)
Greenstone/project.jsonThe mapper project: name, id, operator, vehicle
Greenstone/20261014/One day of survey: the UTC date the session started. A session that runs past midnight stays in the day it started; a second session the same day goes in the same folder.
Greenstone/<Name>.dcsprojThe shared project: captures, shared settings (coordinate system, base station, antennas, Lidar mounting, vehicle) and the state of each stage. A .bak copy is kept beside it.
Greenstone/<Name>.qgzThe QGIS project, when you save it from the project menu
Greenstone/<Name>/The project's folder: 00_RemixPro, 01_PosPro, 02_AlignPro, 03_CloudPro, 04_StripPro (each with its settings file, WORK/, LOG/, and OUT/ with what it finalizes) and EXPORT/, where every deliverable goes by default

A day folder

PathHolds
session.json, events.jsonEvery session of the day, its settings and marks
NAV/nav_20261014_0001.anpp (and .clraw)Navigation recordings: everything the Certus sent while the project was open (no Lidar)
LIDAR/lidar_20261014_0001.pcapThe Lidar packets as recorded; SONAR/ on a boat (the SonarView recordings)
IMU/ins_20261014_0001.anpp, ephemeris_cache.anppThe Certus logs and the ephemeris
CLRAW/20261014_001_001.clrawThe survey lines: line 001 of the day, its first file. MapPro numbers the lines in the order they are recorded and carries on from the highest number in the folder. On a boat RemixPro writes the SonarView recordings here the same way.
BASE/, GNSS/Base station files (added in the office) and the rover's GNSS files (on a boat, the Reach logs)
EXPORT/The mapper's QC report

Lines are recognised from what the files record (their line number and capture), not from their names, so a line split over several files is one line. Navigation recordings are never taken as survey lines.

Jobs from before this layout

Projects made before DCS Core 1.18.0 keep working where they are: Job/Processing/<Name>/<Name>.dcsproj with 01_PosPro, 02_AlignPro, 02_StripPro, 03_CloudPro beside it; nothing is moved. Mapper 2.10 projects (lines/ and nav/ folders) and older capture folders are read as before.

The project can also live on another drive (choose Elsewhere… when you create it). Paths are stored relative to the job folder where possible, so a job can be copied or moved as a whole.

Creating a project

  1. Choose New project… in the project box.
  2. Job folder: the mapper's project folder, the one holding project.json and the day folders (picking a day folder or one of its folders takes the project folder). The project name defaults to the date of the first capture with a number, for example 2026-11-03_1; when that project exists already the next number is offered (2026-11-03_2), so a second processing of the same job (another base station, other settings) gets its own .dcsproj and folder. Type any other name if you prefer.
  3. Processing folder: the job folder by default; Elsewhere… to put the project on another drive.
  4. Press OK. The project is created and opened. {AFTER_CREATE}

A project made in any of the three plugins is the same project: open the .dcsproj in another plugin, or click its box in the header.

When the raw data has moved

If the captures are not where they were (another drive letter, a copied job), {NAME} says so when the project opens and asks for the job folder's new location; Raw data moved? Relocate the job folder… in the project menu does the same at any time. The captures are found again by their place in the job folder; nothing goes out of date because of the move.

Out-of-date results

Each stage records what it was built from. When an earlier stage finalizes again, the raw data changes, or a shared setting it depends on is edited, the stage turns amber (out of date) in the chain in the header, with the reason on hover. Run that stage again to bring it up to date. A run that fails or is cancelled keeps the earlier results.
